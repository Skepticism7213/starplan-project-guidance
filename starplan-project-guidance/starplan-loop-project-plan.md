# 星程 StarPlan Loop 项目总体计划

初始日期：2026-07-18

最近更新：2026-07-26

状态：实施中；将 Claim Registry、受限表达协议和 fail-closed 作为第 3 周 Qwen 编排的加固基线

## 1. 参赛方向

参赛赛道为挑战杯“揭榜挂帅”阿里云榜题：

**赛道三方向三：星语·面向 AI 的天文实训**

赛题要求参赛团队把真实天文工作或科普实践中常用、但尚未很好接入 AI 的任务环节，改造成智能体可以稳定调用的天文 Skills。作品应具备以下特征：

- 可运行
- 可检查
- 可复现
- 可复用
- 有明确的输入、输出、依赖、触发条件和失败处理
- 实际使用阿里云 Qwen 系列模型及相关产品能力

项目不做泛用天文聊天助手，也不以搭建大而全的天文网站为目标。

## 2. 修改后的项目定位

### 项目名称

**星程 StarPlan Loop：面向 AI 的校园天文观测与科普实训闭环 Skills 包**

### 一句话简介

StarPlan Loop 将目标解析、可观测性计算、科普活动设计、实际观测记录和偏差复盘封装为 Qwen 智能体可调用的 AI Ready Skills，让一次校园观测活动能够被计划、执行、检查并持续改进。

### 核心使用场景

主要服务对象为：

- 高校天文社团及其新成员
- 中小学天文科普教师
- 校园公众观测活动组织者
- 本科生天文实训课程

第一使用场景确定为：

> 天文社团希望在指定地点和日期组织一次面向新成员的观测活动，需要判断目标是否适合观测、选择时间、准备讲解和设备，并在活动结束后复盘实际结果。

## 3. 项目要解决的问题

传统观测活动需要组织者在星表、星历、观测计划软件、星图软件和文档工具之间切换。新手容易遗漏时区、目标名称歧义、低高度、月光和设备条件；最终往往只留下截图和活动文档，难以追溯计划依据，也无法系统总结失败原因。

StarPlan Loop 将流程改造为：

```text
自然语言活动需求
-> Qwen 解析为结构化任务
-> 输入确认与业务状态判断
-> 天文工具完成确定性计算
-> 生成带来源的 Allowed Claims
-> Qwen 选择表达顺序和已审核句式
-> 程序验证并渲染观测计划和科普活动包
-> 组织者执行活动并填写观测日志
-> 系统对比计划与实际结果
-> 解释偏差并生成下一次修订计划
```

核心原则：

```text
工具算，Claim 准入，模型编排，程序渲染，报告验，人员确认，日志促改进
```

Qwen 不直接生成高度角、方位角、日落时间、月亮位置和行星坐标等数值，也不能自行补充“肉眼可见”“适合新手”“光污染较低”等文字事实。所有用户可见事实必须先进入本次运行的 Claim Registry，并能追溯到确定性工具、受信数据快照、版本化推导规则或人工确认。

默认安全模式下，Qwen 只选择 `claim_id`、已审核的 `sentence_variant_id`、顺序和语气标签；事实句由程序渲染。原始模型文本不得直接成为最终用户输出。验证失败、模型不可用或输出格式错误时，系统必须返回确定性回退结果，不能返回被阻断的原文。

## 4. 项目目标

### 科学目标

- 对目标、地点、日期和设备进行规范化处理。
- 可靠计算高度角、方位角、airmass、暮光和月光影响。
- 给出带依据的推荐窗口、风险说明和备选方案。
- 让科普文案严格依据计算结果和经过审核的 Claims，由程序控制事实句渲染。

### 技术目标

- 交付可以单独调用、也可以由总控串联的 Skills 包。
- 为每个 Skill 定义输入、输出、触发条件、依赖和失败处理。
- 使用 Qwen/阿里云百炼完成自然语言解析、工具调用编排和科普表达。
- 使用 Claim Registry、结构化表达计划和确定性渲染约束模型输出。
- 保存模型版本、工具版本、调用链、Claim 来源、验证结果和关键中间结果。
- 将可观测、不可观测、目标待确认、数据不足、工具错误和验证阻断建模为独立状态。
- 在无在线天文服务时，核心观测计算仍能复现。
- 在 Qwen 不可用或输出验证失败时，核心结果仍能离线生成并安全返回。

### 应用目标

- 让天文社团新成员能理解推荐时间是如何产生的。
- 降低组织校园观测活动的准备成本和专业门槛。
- 在活动失败或效果不佳时，给出可检查的偏差归因和下一轮改进建议。
- 形成可以用于社团培训、课堂实训和公众科普的标准活动记录。

## 5. 核心 Skills 设计

首期收敛为 4 个核心 Skill 和 1 个总控入口。星图和图表作为计算结果的展示层，不单独拆成 Skill；太阳系星历作为后续扩展，避免首期范围过大。

| Skill | 主要职责 | 典型输入 | 主要输出 | 关键失败处理 |
|---|---|---|---|---|
| `target_resolve` | 将中文名、英文名或别名解析为标准目标 | 目标名称、可选目标类型 | 标准名称、类型、坐标、来源、置信度 | 名称歧义时列出候选并要求人工确认 |
| `observability_plan` | 计算目标是否可观测并生成计划 | 目标坐标、地点、日期、设备约束 | 可见窗口、高度/方位、airmass、暮光和月光风险、备选时段 | 地点、时区或日期不完整时停止计算并返回缺失项 |
| `outreach_pack` | 把验证后的 Claims 转成适合目标受众的科普活动包 | Claim Registry、计算结果、受众、设备 | 活动流程、讲解词、Claim 映射、设备清单、安全提示、人工核对项 | 未知 Claim、格式错误或模型失败时丢弃模型结果并使用确定性模板 |
| `observation_review` | 对比计划和实际日志并修订下一轮计划 | 原计划、结构化日志、Evidence Claims | 偏差分类、证据引用、改进建议、修订后的下一次计划 | 证据不足时只能标记 `possible` 或 `undetermined`，不得生成确定归因 |

总控入口：

```text
starplan.run
```

总控负责识别用户意图、依次调用必要 Skill、维护业务状态、构建 Claims、执行验证和确定性回退、保存运行目录，并把机器可读结果和人类可读报告一起返回。

总控状态至少区分：`NEEDS_CONFIRMATION`、`COMPUTED_OBSERVABLE`、`COMPUTED_NOT_OBSERVABLE`、`DATA_INSUFFICIENT`、`TOOL_ERROR` 和 `VALIDATION_BLOCKED`。其中“不可观测”是成功计算出的业务结论，不能与工具失败或数据不足混为一谈。

## 6. 数据流与输出规范

### 可信输出数据流

```text
结构化输入
-> 确定性工具结果
-> Allowed Claims Builder
-> claims.json
-> Qwen 结构化表达计划（可选）
-> Claim/句式/状态验证
-> 程序渲染或确定性回退
-> RunOutcome
-> Manifest + Validation Report + 用户输出
```

Claim Registry 必须同时约束 Qwen 输出、确定性模板、回退文本和复盘归因。模板中的固定文字不因“来自代码”而自动可信。

### 统一输入示例

```json
{
  "target": "M31",
  "location": "济南_四门塔",
  "date_range": ["2026-10-17", "2026-10-17"],
  "audience": "天文社新成员",
  "equipment": "binoculars",
  "goal": "校园科普观测"
}
```

### 统一运行目录

每次运行生成独立目录，建议包括：

```text
runs/case_xxx/
  input.json
  resolved_target.json
  claims.json
  expression_plan.json
  render_trace.json
  run_outcome.json
  calculation_manifest.json
  observability.csv
  visibility_curve.png
  plan.json
  outreach_pack.md
  observation_log.csv
  review_report.md
  revised_plan.json
  validation_report.md
  model_call_log.jsonl
  audit_events.jsonl
```

`run_outcome.json` 是业务状态、验证状态和交付状态的单一事实来源。`calculation_manifest.json` 和 `validation_report.md` 必须从同一个 RunOutcome 生成，不能各自推断或回写状态。

`calculation_manifest.json` 是本项目的重要证据文件，至少记录：

- `schema_version`
- 输入地点、时区和时间范围
- 目标来源和坐标
- 使用的天文工具及版本
- 主要约束规则
- 数据快照、Claim Registry、规则和模板版本
- 业务状态、验证状态和交付状态
- 从真实 `model_call` 审计事件反推的模型使用状态
- 中间计算结果文件
- 人工修改和确认记录
- 关键输入、输出和产物哈希

每个用户可见事实句必须在 `render_trace.json` 中映射到一个或多个 Claim ID。模型调用日志和被阻断原文只用于审计，不得泄漏 API Key、token、私人数据或内部提示词。

## 7. MVP 范围

### 第一阶段必须完成

- 常用目标别名解析和名称歧义处理。
- 固定恒星及深空目标的本地可观测性计算。
- 高度角、airmass、暮光和月光影响分析。
- 带理由的推荐窗口、风险和备选时间。
- Claim Registry、结构化表达计划和确定性渲染组成的 Qwen 科普活动包。
- 可观测、不可观测、目标待确认、数据不足、工具错误和验证阻断的完整失败路径。
- Qwen 不可用时仍能生成的离线确定性活动包和结果摘要。
- CSV 观测日志导入、偏差归因和修订计划。
- 一个轻量网页调用面板或等价演示入口。
- 3 组完整案例、自动测试和复现文档。

### 第二阶段再考虑

- 行星和太阳系目标的权威星历接入。
- Stellarium 脚本或 Aladin Lite 交互星图。
- 校园地平线遮挡模型。
- 更多天象模板和多语言科普材料。

### 暂不进入范围

- 望远镜硬件控制
- 实时天气预报系统
- 账户、社区和长期内容平台
- 覆盖所有类型天体和天象
- 模型微调、多智能体系统和复杂 3D 前端

## 8. 三类典型案例

### 案例一：正常可观测活动

济南高校天文社计划组织 M31 新生观测夜（观测地点：四门塔景区）。系统生成目标信息、推荐时段、高度曲线、设备建议和讲解包，人工确认后形成活动计划。

### 案例二：不适合观测及备选方案

用户输入的目标在指定时间高度过低、受月光影响或处于暮光阶段。系统不能只返回“不推荐”，还要展示触发的规则、计算依据和可替换的时间或目标。

### 案例三：实际活动复盘

导入一份包含迟到、云量增加、器材准备不足或目标选取不当的观测日志。系统区分可计算因素与人工记录因素，生成偏差报告并修订下一次活动计划。

若核心流程提前稳定，可增加土星观测作为太阳系扩展示例，但不得影响上述三类案例的完整性。

## 9. 验证与评测计划

### 科学准确性

- 使用成熟天文软件或公开权威结果对固定案例进行交叉校验。
- 检查目标坐标、时区、太阳高度、目标高度和推荐窗口。
- 保存参考结果、差异和人工确认结论。

### 模型可靠性

- 检查所有用户可见事实是否具有 Claim ID、来源、作用域和渲染映射。
- 使用 Mock Qwen 注入纯文字幻觉、合法 Claim 夹带新事实、错误单位/时区、伪造 Claim、提示注入、非法 JSON 和空响应。
- 断言验证失败时原始模型内容不会出现在最终输出，系统改用确定性回退。
- 比较裸 Qwen、旧式自由文本过滤和 Claim Registry 模式的无来源事实率、阻断率、回退率和人工核查时间。
- 少量真实 Qwen canary 只验证模型/API 兼容性，不替代离线科学和对抗测试。

### 闭环有效性

- 设计至少 3 类观测偏差：时间偏差、环境影响、设备或操作问题。
- 检查复盘结果是否引用了计划和日志证据。
- 检查下一次计划是否真实修改了相应参数，而不是重复原建议。

### 可复现性

- 在新的运行环境按 README 完成安装和固定案例复跑。
- 确保相同版本、相同输入能产生一致的计算结果。
- API Key 仅影响 Qwen 表达层，核心计算和示例结果应有离线复现方式。
- 验证 Manifest、Validation Report、用户输出和审计事件的状态一致，并核对关键产物哈希。

## 13. 项目成功标准

项目达到以下条件才视为完成：

- 不是聊天演示，而是可以直接调用的 Skills 包。
- 至少一个核心案例从计划、执行记录到修订计划完整闭环。
- 至少三类任务具有可复现运行记录。
- 所有用户可见事实都能通过 Claim 映射追溯到工具、受信数据、推导规则或人工确认。
- 用户可见无来源事实率为 0，验证失败原文泄漏率为 0，事实 Claim 映射覆盖率为 100%。
- 可观测、不可观测、目标待确认、数据不足、工具错误和验证阻断均有确定性输出。
- Manifest、Validation Report、审计事件和用户输出状态一致。
- Qwen 的作用、边界和调用证据清楚。
- 评委可以在有限时间内看懂任务价值、运行过程和创新点。
- 团队成员能解释每个模块的输入、输出、依赖、失败处理和验证方式。
