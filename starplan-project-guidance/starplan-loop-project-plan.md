# 星程 StarPlan Loop 项目总体计划

初始日期：2026-07-18

最近更新：2026-08-02

状态：实施中；四个核心 Skills 和可信输出基础已形成，但第 3 周可信输出验收、第 4 周可执行复盘闭环、第 5 周智能体交付与三类案例仍未完成。当前进入 2026-09-01 初赛提交倒排阶段。

## 1. 参赛方向

参赛赛道为挑战杯“揭榜挂帅”阿里云榜题：

**赛道三方向三：星语·面向 AI 的天文实训**

赛题要求参赛团队把真实天文工作或科普实践中常用、但尚未很好接入 AI 的任务环节，改造成智能体可以稳定调用的天文 Skills。作品应具备以下特征：

- 可运行
- 可检查
- 可复现
- 可复用
- 有明确的输入、输出、依赖、触发条件和失败处理
- 实际使用阿里云 Qwen 系列模型及相关产品能力

项目不做泛用天文聊天助手，也不以搭建大而全的天文网站为目标。

## 2. 当前项目定位（2026-08-02 冻结）

### 项目名称

**星程 StarPlan Loop：面向学校与青少年科普活动的可信 AI Ready 天文实训闭环 Skills 包**

### 一句话简介

StarPlan Loop 将目标解析、可观测性计算、分众科普表达、活动执行记录和证据复盘封装为 Qwen 智能体可调用的 AI Ready Skills，让学校和青少年天文活动能够被计划、执行、检查、复现并持续改进。

### 核心使用场景

主要服务对象为没有专业天文软件使用经验、但需要组织观测或教学活动的人，包括：

- 中小学科学教师、科技辅导员和青少年科普活动组织者
- 高校天文社团及其新成员
- 校园公众观测活动组织者
- 中小学科学课程、社团活动和本科生天文实训课程

一次运行至少区分三类信息接收者：

- **组织者**：关注时间、场地、设备、人员、安全条件和失败预案。
- **教师或讲解员**：关注讲解顺序、科学依据、适龄表达和人工核对项。
- **学生或参与者**：关注与年龄和经验相符的观察任务、提问和理解提示。

三类输出必须共享同一 Claim Registry，只允许改变组织方式、语言难度和互动形式，不得改变科学事实。

第一使用场景确定为：

> 学校教师、天文社团或科普组织者希望在指定地点和日期，为中小学生或社团新成员组织一次观测活动，需要判断目标是否适合观测、安排现实活动时段、准备分众讲解与安全清单，并在活动结束后依据真实记录生成下一轮可执行计划。

## 3. 项目要解决的问题

传统观测活动需要组织者在星表、星历、观测计划软件、星图软件和文档工具之间切换。新手容易遗漏时区、目标名称歧义、低高度、月光和设备条件；最终往往只留下截图和活动文档，难以追溯计划依据，也无法系统总结失败原因。

StarPlan Loop 将流程改造为：

```text
自然语言活动需求
-> Qwen 解析为结构化任务
-> 输入确认与业务状态判断
-> 天文工具完成确定性计算
-> 生成带来源的 Allowed Claims
-> Qwen 选择表达顺序和已审核句式
-> 程序验证并渲染观测计划和科普活动包
-> 组织者执行活动并填写观测日志
-> 系统对比计划与实际结果
-> 解释偏差并生成下一次修订计划
```

核心原则：

```text
工具算，Claim 准入，模型编排，程序渲染，报告验，人员确认，日志促改进
```

Qwen 不直接生成高度角、方位角、日落时间、月亮位置和行星坐标等数值，也不能自行补充“肉眼可见”“适合新手”“光污染较低”等文字事实。所有用户可见事实必须先进入本次运行的 Claim Registry，并能追溯到确定性工具、受信数据快照、版本化推导规则或人工确认。

默认安全模式下，Qwen 只选择 `claim_id`、已审核的 `sentence_variant_id`、顺序和语气标签；事实句由程序渲染。原始模型文本不得直接成为最终用户输出。验证失败、模型不可用或输出格式错误时，系统必须返回确定性回退结果，不能返回被阻断的原文。

## 4. 项目目标

### 科学目标

- 对目标、地点、日期和设备进行规范化处理。
- 可靠计算高度角、方位角、airmass、暮光和月光影响。
- 给出带依据的推荐窗口、风险说明和备选方案。
- 让科普文案严格依据计算结果和经过审核的 Claims，由程序控制事实句渲染。

### 技术目标

- 交付可以单独调用、也可以由总控串联的 Skills 包。
- 交付至少一种可被 Qwen 智能体直接加载或调用的标准入口，并在干净环境验证安装、触发和返回结果。
- 为每个 Skill 定义输入、输出、触发条件、依赖和失败处理。
- 使用 Qwen/阿里云百炼完成自然语言解析、工具调用编排和科普表达。
- 使用 Claim Registry、结构化表达计划和确定性渲染约束模型输出。
- 保存模型版本、工具版本、调用链、Claim 来源、验证结果和关键中间结果。
- 将可观测、不可观测、目标待确认、数据不足、工具错误和验证阻断建模为独立状态。
- 在无在线天文服务时，核心观测计算仍能复现。
- 在 Qwen 不可用或输出验证失败时，核心结果仍能离线生成并安全返回。

### 应用目标

- 让中小学生、社团新成员和非专业组织者能理解推荐时间是如何产生的。
- 降低学校和青少年天文观测活动的准备成本和专业门槛。
- 让同一组可信科学事实可以转化为组织者、教师或讲解员、学生三类适场景输出。
- 在活动失败或效果不佳时，给出可检查的偏差归因和下一轮改进建议。
- 形成可以用于社团培训、课堂实训和公众科普的标准活动记录。

## 5. 核心 Skills 设计

首期收敛为 4 个核心 Skill 和 1 个总控入口。星图和图表作为计算结果的展示层，不单独拆成 Skill；太阳系星历作为后续扩展，避免首期范围过大。

| Skill | 主要职责 | 典型输入 | 主要输出 | 关键失败处理 |
|---|---|---|---|---|
| `target_resolve` | 将中文名、英文名或别名解析为标准目标 | 目标名称、可选目标类型 | 标准名称、类型、坐标、来源、置信度 | 名称歧义时列出候选并要求人工确认 |
| `observability_plan` | 计算目标是否可观测并生成计划 | 目标坐标、地点、日期、设备约束 | 可见窗口、高度/方位、airmass、暮光和月光风险、备选时段 | 地点、时区或日期不完整时停止计算并返回缺失项 |
| `outreach_pack` | 把验证后的 Claims 转成适合目标受众和角色的活动包 | Claim Registry、计算结果、年龄/经验、角色、设备 | 组织者流程、适龄讲解、学生观察任务、Claim 映射、设备与安全清单、人工核对项 | 未知 Claim、格式错误或模型失败时丢弃模型结果并使用确定性模板 |
| `observation_review` | 对比计划和实际日志并生成可再次运行的下一轮计划 | 原计划、结构化日志、Evidence Claims | 偏差分类、证据引用、改进建议、`next_activity_input.json` 或等价可执行输入 | 证据不足时只能标记 `possible` 或 `undetermined`；不可执行的文字建议不能冒充下一轮计划 |

总控入口：

```text
starplan.run
```

总控负责识别用户意图、依次调用必要 Skill、维护业务状态、构建 Claims、执行验证和确定性回退、保存运行目录，并把机器可读结果和人类可读报告一起返回。

总控状态至少区分：`NEEDS_CONFIRMATION`、`COMPUTED_OBSERVABLE`、`COMPUTED_NOT_OBSERVABLE`、`DATA_INSUFFICIENT`、`TOOL_ERROR` 和 `VALIDATION_BLOCKED`。其中“不可观测”是成功计算出的业务结论，不能与工具失败或数据不足混为一谈。

## 6. 数据流与输出规范

### 可信输出数据流

```text
结构化输入
-> 确定性工具结果
-> Allowed Claims Builder
-> claims.json
-> Qwen 结构化表达计划（可选）
-> Claim/句式/状态验证
-> 程序渲染或确定性回退
-> RunOutcome
-> Manifest + Validation Report + 用户输出
```

Claim Registry 必须同时约束 Qwen 输出、确定性模板、回退文本和复盘归因。模板中的固定文字不因“来自代码”而自动可信。

### 统一输入示例

```json
{
  "target": "M31",
  "location": "济南_四门塔",
  "date_range": ["2026-10-17", "2026-10-17"],
  "audience": "天文社新成员",
  "equipment": "binoculars",
  "goal": "校园科普观测"
}
```

### 统一运行目录

每次运行生成独立目录，建议包括：

```text
runs/case_xxx/
  input.json
  resolved_target.json
  claims.json
  expression_plan.json
  render_trace.json
  run_outcome.json
  calculation_manifest.json
  observability.csv
  visibility_curve.png
  plan.json
  outreach_pack.md
  observation_log.csv
  review_report.md
  revised_plan.json
  validation_report.md
  model_call_log.jsonl
  audit_events.jsonl
```

`run_outcome.json` 是业务状态、验证状态和交付状态的单一事实来源。`calculation_manifest.json` 和 `validation_report.md` 必须从同一个 RunOutcome 生成，不能各自推断或回写状态。

`calculation_manifest.json` 是本项目的重要证据文件，至少记录：

- `schema_version`
- 输入地点、时区和时间范围
- 目标来源和坐标
- 使用的天文工具及版本
- 主要约束规则
- 数据快照、Claim Registry、规则和模板版本
- 业务状态、验证状态和交付状态
- 从真实 `model_call` 审计事件反推的模型使用状态
- 中间计算结果文件
- 人工修改和确认记录
- 关键输入、输出和产物哈希

每个用户可见事实句必须在 `render_trace.json` 中映射到一个或多个 Claim ID。模型调用日志和被阻断原文只用于审计，不得泄漏 API Key、token、私人数据或内部提示词。

## 7. MVP 范围

### 第一阶段必须完成

- 常用目标别名解析和名称歧义处理。
- 固定恒星及深空目标的本地可观测性计算。
- 高度角、airmass、暮光和月光影响分析。
- 带理由的科学可见窗口、60 至 120 分钟现实活动时段、准备/收尾时间、风险和备选时间。
- Claim Registry、结构化表达计划和确定性渲染组成的 Qwen 科普活动包。
- 面向组织者、教师或讲解员、学生的分众输出；至少覆盖一个中小学生年龄段和一个高校/成人新手场景。
- 面向未成年人活动的确定性安全与人工确认清单；模型不能自动确认场地许可、监护、交通和现场安全。
- 可观测、不可观测、目标待确认、数据不足、工具错误和验证阻断的完整失败路径。
- Qwen 不可用时仍能生成的离线确定性活动包和结果摘要。
- CSV 观测日志导入、偏差归因、可执行下一轮输入和 before/after 活动包。
- 可由 Qwen 智能体直接加载或调用、能显示 Skill 触发和关键阶段状态的演示入口；自建网页不是核心验收项。
- 3 组完整案例、自动测试、人工校验入口和干净环境复现文档。

### 第二阶段再考虑

- 行星和太阳系目标的权威星历接入。
- Stellarium 脚本或 Aladin Lite 交互星图。
- 校园地平线遮挡模型。
- 更多天象模板和多语言科普材料。

### 暂不进入范围

- 望远镜硬件控制
- 实时天气预报系统
- 账户、社区和长期内容平台
- 覆盖所有类型天体和天象
- 模型微调、多智能体系统和复杂 3D 前端

## 8. 三类典型案例

### 案例一：正常可观测活动

济南的学校教师、青少年科普组织者或高校天文社计划组织 M31 新手观测活动。系统生成目标信息、科学可见窗口、现实活动时段、高度曲线、设备与安全清单，并从同一 Claims 生成组织者版、讲解员版和学生版内容。

### 案例二：不适合观测及备选方案

用户输入的目标在指定时间高度过低、受月光影响或处于暮光阶段。系统不能只返回“不推荐”，还要展示触发的规则、计算依据和可替换的时间或目标。

### 案例三：实际活动复盘

导入一份包含迟到、云量增加、器材准备不足、目标未找到或学生理解困难的观测日志。系统区分可计算因素、人工记录因素和无法判断事项，生成偏差报告、可执行下一轮输入和重新渲染的活动包，并展示 before/after 差异。

三类案例的完整运行记录都必须保留：原始输入、Skill 触发链、关键中间结果、Qwen 采用或拒绝记录、最终输出、验证结果和人工校验入口。案例三优先使用 2026 年 8 月中旬小规模实地观测数据；若天气或场地导致取消，也应如实作为失败路径证据。无法实地完成时，必须将桌面演练和模拟数据明确标注。

若核心流程提前稳定，可增加土星观测作为太阳系扩展示例，但不得影响上述三类案例的完整性。

## 9. 验证与评测计划

### 科学准确性

- 使用成熟天文软件或公开权威结果对固定案例进行交叉校验。
- 检查目标坐标、时区、太阳高度、目标高度和推荐窗口。
- 保存参考结果、差异和人工确认结论。
- 提交前争取由一名物理教师、天文社成员或有经验的天文爱好者对三个核心案例进行可留痕复核；Qwen/GPT 交叉审查不能替代外部领域复核。

### 模型可靠性

- 检查所有用户可见事实是否具有 Claim ID、来源、作用域和渲染映射。
- 使用 Mock Qwen 注入纯文字幻觉、合法 Claim 夹带新事实、错误单位/时区、伪造 Claim、提示注入、非法 JSON 和空响应。
- 断言验证失败时原始模型内容不会出现在最终输出，系统改用确定性回退。
- 比较裸 Qwen、旧式自由文本过滤和 Claim Registry 模式的无来源事实率、阻断率、回退率和人工核查时间。
- 少量真实 Qwen canary 只验证模型/API 兼容性，不替代离线科学和对抗测试。

### 闭环有效性

- 设计至少 3 类观测偏差：时间偏差、环境影响、设备或操作问题。
- 检查复盘结果是否引用了计划和日志证据。
- 检查下一次计划是否真实修改了相应参数，而不是重复原建议。
- 检查下一轮输出是否符合 runner 输入 Schema，并能实际重新运行、重新生成活动包和显示可追溯差异。

### 场景与分众有效性

- 同一 Claim Registry 至少生成组织者、教师或讲解员、学生三种输出。
- 检查语言难度、活动任务和安全提示是否符合所选年龄与角色，同时保持科学事实一致。
- 通过小规模实地活动或明确标注的桌面演练记录准备用时、目标找到情况、参与者理解反馈和人工修改。

### 可复现性

- 在新的运行环境按 README 完成安装和固定案例复跑。
- 确保相同版本、相同输入能产生一致的计算结果。
- API Key 仅影响 Qwen 表达层，核心计算和示例结果应有离线复现方式。
- 验证 Manifest、Validation Report、用户输出和审计事件的状态一致，并核对关键产物哈希。
- 在没有用户 Astropy 缓存、没有 API Key、Qwen 超时或不可用的条件下，三类案例仍应在规定时限内进入清晰的成功、不可观测或安全回退状态。

## 10. 最终成果形式

### 核心作品

1. **StarPlan Loop Skills 包**
   - Skills 定义文件
   - Python 源码和统一调用入口
   - 安装、依赖、调用示例和失败说明
   - 阿里云百炼/Qwen 接入配置说明

2. **Qwen 智能体演示与调用入口**
   - Skills 包可以被智能体直接加载或通过标准调用入口触发
   - 用户以自然语言提出目标、地点、日期、受众和设备需求
   - 演示中明确显示触发了哪个 Skill、确定性计算阶段、Qwen 作用和回退状态
   - 导入日志后能够展示复盘、可执行下一轮输入和重新生成的活动包
   - 独立网页仅作为可选加分项，不得挤占 Skills 可加载性、三个案例和材料制作

3. **复现与评测材料**
   - 3 组完整运行记录
   - 固定评测集和自动测试
   - 科学交叉校验记录
   - Claims、RunOutcome、Qwen 调用日志和模型约束说明
   - 裸 Qwen、旧过滤器和 Claim Registry 模式的对抗评测
   - 开源工具来源、许可证和改造说明

### 赛事提交材料

- 截止时间：**2026-09-01 00:00:00（北京时间）**。
- 一份不超过 20 页的 PPT/PDF，清楚索引全部交付物和证据。
- 可直接运行或加载到智能体的 Skills 包，含依赖说明、安装方式和调用示例。
- Skills 流程图和清单，说明问题、触发条件、输入、输出和失败处理。
- 至少 3 类典型任务的完整运行记录，保留关键中间结果、最终输出和人工校验入口。
- 已有天文工具或开源项目的来源、许可证、改造内容和智能体调用方式。
- 应用技术报告和源码。
- 附加提交为可交互前端页面或 10 分钟内演示视频；本项目优先制作 6 至 8 分钟演示视频，前端为可选项。

### 演示视频与评委复现主线

```text
向 Qwen 智能体输入学校或青少年观测需求
```

## 13. 项目成功标准

项目达到以下条件才视为完成：

- 不是聊天演示，而是可以直接调用的 Skills 包。
- Skills 包至少在一种 Qwen 智能体环境完成从加载、触发到返回结果的真实验证。
- 至少一个核心案例从计划、执行记录到修订计划完整闭环。
- 至少三类任务具有可复现运行记录。
- 至少一个正常案例从同一 Claims 生成组织者、教师或讲解员、学生三类事实一致的输出。
- 科学可见窗口和现实活动时段分开表达，不默认生成不合理的通宵青少年活动。
- `observation_review` 生成的下一轮输入能够再次进入 runner，并产生可见、可追溯的计划变化。
- 所有用户可见事实都能通过 Claim 映射追溯到工具、受信数据、推导规则或人工确认。
- 用户可见无来源事实率为 0，验证失败原文泄漏率为 0，事实 Claim 映射覆盖率为 100%。
- 可观测、不可观测、目标待确认、数据不足、工具错误和验证阻断均有确定性输出。
- Manifest、Validation Report、审计事件和用户输出状态一致。
- Qwen 的作用、边界和调用证据清楚。
- 评委可以只阅读 20 页内材料和 10 分钟内视频，就看懂任务价值、运行过程、创新点和复现方式。
- 团队成员能解释每个模块的输入、输出、依赖、失败处理和验证方式。
