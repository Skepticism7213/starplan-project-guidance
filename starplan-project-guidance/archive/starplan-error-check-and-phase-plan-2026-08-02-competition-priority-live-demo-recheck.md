# StarPlan 错误检查与阶段计划 - 竞赛优先级与真实演示复查（2026-08-02）

## 1. 复查目的与结论

本轮不再只按软件架构严重度排序，而是回到阿里“挑战杯”赛道的核心目标：在有限开发时间和 10 分钟演示内，证明 StarPlan 是一个有科学可信度、有 Qwen/Skills 技术深度、能形成校园天文实训闭环、并且现场可稳定运行的作品。

结论如下：

1. 上轮问题中确有一部分属于“技术答辩前的可信度硬化”，不应抢在演示闭环之前。尤其是取证级防篡改、每个 source hash 的完整精细化、全量隐私保留策略，不是当前最高收益项。
2. 但 IERS 导致 README 案例 180 秒卡死、当前 Chat 78.7 秒且状态互相矛盾、M31 生成九小时活动安排、案例三没有产出可直接进入下一轮的计划，这些会被评委直接观察到，会真实降低竞争力，不是“为了修而修”。
3. 阿里云账户恢复后，M31 结构化、案例三复盘、中文 Chat 共完成 8 次真实百炼调用，全部成功；本轮未再出现欠费、容量或空响应错误。模型连通性已恢复。
4. 当前最稳的比赛主线不应使用 `run_starplan_chat()` 作为现场主入口。建议使用轻量表单或受控自然语言解析进入统一结构化 runner，Qwen 最多承担一次 ExpressionPlan 选择；Chat 暂作技术展示或备用路径，待状态合同和耗时修复后再决定是否进入主演示。
5. 本文提出的演示策略和优先级为待项目负责人确认的建议，尚未正式修改 `starplan-loop-project-plan.md`。

## 2. Error Check

### CRITICAL C-01：README 原样运行在计算阶段卡死 180 秒

**真实复现**：按 README 执行：

```text
python scripts/run_case.py examples/case_01_m31_jinan.json
```

180 秒后超时。运行目录只包含 `input.json`、`resolved_target.json` 和 `state_log.json`，状态停在 `ready_to_compute`，尚未调用百炼。

**竞争力影响**：这是现场演示一级阻断项。评委不会区分 IERS 缓存、Astropy 联网与业务代码；长时间无结果会被直接理解为程序卡死或不可复现。

**建议**：把 IERS/leap-second 离线策略放入正常计算入口，并在新环境、空缓存、禁网条件下跑 README 三案例。不要依靠 `conftest.py` 或演示人员手工设置。

**验收**：README M31/M42 在无 API、无用户 Astropy 缓存时 15 秒内进入可交付结果；不得等待远端 IERS 更新。

### CRITICAL C-02：当前 Chat 不适合作为现场主入口

**真实结果**：中文自然语言 M31 Chat 成功调用：

```text
target_resolve -> resolve_location -> observability_plan -> outreach_pack
```

但总耗时 78.7 秒，发起 5 次模型调用。最终 `run_outcome.json` 为 observable / passed / qwen_expression_plan，公共字段 `public_output_validation` 却为 blocked；模型日志为 5 次，Outcome 只记 1 次；Chat 没有生成 Manifest 和 Validation Report。

**竞争力影响**：现场等待接近 80 秒会压缩讲解时间；同一 run 同时出现 passed 与 blocked，会削弱可信度叙事；缺少 Manifest/Report 会直接破坏“观测配方和证据链”这一核心卖点。

**建议**：

1. 主演示改用结构化 runner 或“单次 Qwen 解析/选择 + 结构化 runner”，避免多轮自由 Chat。
2. UI 立即显示阶段进度：目标解析、天文计算、Claim 构建、Qwen 选择、合同验证、完成。
3. 模型调用设置现场超时；超时后清楚显示“Qwen 不可用，已切换确定性模板”，继续交付核心结果。
4. Chat 未统一 Manifest/Report、Outcome 和最终文本合同前，不在主演示中展示其 `public_output_validation`。

**验收**：点击后 1 秒内显示进度；本地计算 10 秒内完成；Qwen 超时不超过团队确定的现场阈值（建议 30-35 秒）；失败后仍可继续演示完整结果。

### CRITICAL C-03：M31 输出把科学可见窗口误当成九小时活动时段

真实 M31 输出推荐 `19:13 ~ 04:28`，活动流程写成从 19:13 持续观测到 04:28。这个时段是满足高度/airmass 约束的科学可见窗口，不是适合天文社新成员的校园活动时长。

**竞争力影响**：评委可能认为项目只会做天文计算，没有理解校园活动组织场景；这会削弱应用价值和产品完成度。

**建议**：明确拆分：

- `scientific_visibility_window`：完整可见窗口，保留科学依据；
- `recommended_activity_slot`：在可见窗口内选择 60-120 分钟的活动时段；
- `setup_time` / `cleanup_time`：围绕活动时段生成现实流程。

活动时段规则应由配置或人类选择决定，Qwen 只能选择批准的候选时段，不能自由发明。

**验收**：新成员案例不再默认生成通宵活动；UI 同时展示“整夜可见范围”和“建议活动时段”，避免把两者混为一谈。

### CRITICAL C-04：案例三仍未形成可执行的下一轮计划

真实复盘在 63.71 秒内完成，找到 3 类偏差、5 个原因、5 条建议、3 个修订字段。Qwen review 返回 rejected，最终采用规则结果，未发生本轮文字幻觉。

但 `revised_plan.json` 只是修订清单：增加准备步骤、设备预检、预期管理。它不能直接作为下一轮 runner 输入，也没有重新生成变化后的活动流程。严格来说当前是“复盘 + 建议”，还不是“日志真正促成下一轮计划”的完整闭环。

**竞争力影响**：计划到复盘的参数变化是本项目区别于普通天文规划/聊天机器人的核心创新。若评委发现“下一次计划”不能再次运行，闭环叙事会明显减分。

**建议**：

1. 输出 schema 化的 `next_activity_input.json` 或 `next_plan_patch.json`。
2. 至少支持可执行字段：到场提前量、设备预检开关、预期说明开关、备选活动、目标/日期替换建议。
3. 将 patch 应用到下一轮活动包，生成 before/after 差异；演示时直接展示流程新增或时间改变。
4. 在 review ID-only 完成前，现场关闭 Qwen 自由补充，仅使用确定性规则和 Evidence Claims，避免为一次被拒绝的模型调用增加 30 秒以上等待。

**验收**：点击“生成下一轮”后得到符合 schema 的输入和新活动包；至少一个流程或计划字段发生可见变化，并能追溯到日志证据。

### CRITICAL C-05：尚无轻量演示应用，当前只有 CLI 和文件输出

仓库中没有 Gradio、Streamlit、Web 或等价演示入口。现有高度角曲线清晰，Markdown 活动包和证据文件也可用，但需要人工在终端和文件管理器之间切换。

**竞争力影响**：项目计划第 5 周明确要求轻量演示入口。10 分钟答辩中逐个打开 JSON/Markdown 会分散注意力，使评委难以快速理解“输入 -> 计算 -> 活动包 -> 日志 -> 下一轮”的主线。

**建议**：只做一页轻量界面，不做复杂前端：

1. 左侧：目标、地点、日期、受众、设备和三个预载案例。
2. 中间：阶段进度、业务状态、推荐活动时段、主要风险和高度曲线。
3. 右侧：Claim 来源卡、活动包、导入日志、复盘差异和“生成下一轮”。
4. 顶部固定显示：本地计算 / Qwen 选择 / 确定性回退 / 合同状态。
5. 提供“实时运行”和“打开已验证运行”两个按钮；后者必须明确标注为复现历史结果，不能伪装成实时调用。

**验收**：不打开终端即可跑三个案例；评委在 30 秒内能看懂当前步骤、科学依据、Qwen 作用和失败回退。

### WARNING W-01：演示数据和用户文案有明显矛盾或不够成品化

1. 未来日期 2026-10-17 的讲解仍写“今晚我们要观测的是 M31”。应改为“本次活动”或显示具体日期。
2. M42 控制台写“夜间最高高度仅 -5.7°”，活动包又显示“目标高度角 -58.7°”，后者是某个采样点而非最高高度，容易被理解为数值冲突。
3. 复盘按计划窗口计算“晚 16 分钟”，示例备注又写“迟到 30 分钟”，同一报告出现两个延迟量。
4. 偏差标题使用 `time偏差`、`environment偏差`，计划修订表为每行重复一次表头。

**建议**：这些不是大架构问题，但都是低成本、高可见度的赛前修正。统一基准值、中文标签和 Markdown 表格；示例备注不要重复记录与结构化时间冲突的数字。

### WARNING W-02：Skills 包和文档版本漂移会削弱工程可信度

`starplan_skills.__version__` 为 0.4.0，`skills.yaml` 仍为 0.2.0；`skills.yaml` 还声称 observation_review 基于 Evidence Claims、输出目录为 `runs/case_{run_id}/`，与当前实现不完全一致。

**竞争力影响**：评委或技术专家检查 Skills 定义时会怀疑文档和代码不是同一交付版本。

**建议**：演示冻结前统一 package、skills.yaml、README、Schema 和报告版本；只保留已经通过验收的能力声明。

### WARNING W-03：模型调用证据在真实复盘中仍不一致

真实案例三日志包含 `expression_plan` 和 `review_attribution` 两次模型调用，Outcome/Manifest 只记录 1 次。虽然不会改变活动结果，但会损伤“Qwen 调用过程可追踪”的答辩证据。

**建议**：从真实模型日志聚合调用次数、成功/失败/接受/拒绝状态。演示页应显示：调用了几次、哪次结果被采用、哪次被拒绝及回退方式。

### WARNING W-04：上轮 Claim 语义和证据文件问题需要重排，而不是全部立即重构

| 上轮问题 | 竞赛优先级 | 判断 |
|---|---|---|
| Claim 文本不能由 Claim + variant 重放 | P1，技术答辩前完成 | 是核心创新的可证明性问题，但正常 Qwen 当前不能直接写 `final_text`，不是现场首要崩溃点 |
| 非法 `claims.json` / `expression_plan.json` 仍 pass | P2，演示闭环后完成 | 做基本 schema/一致性校验即可；暂不需要取证级防篡改系统 |
| 结构化 BLOCKED 仍返回活动包 | P0 | 修复成本低，直接影响失败案例可信度 |
| Chat BLOCKED 仍返回事实 | P0（若展示 Chat） | 若采用结构化主演示，可先从主路径移除 Chat，再并行修复 |
| Review 自由文本幻觉 | P0 | 复盘是核心差异；完成 ID-only 前应禁用自由补充 |
| source hash 未绑定全部值 | P2 | 技术报告前补齐，不应阻塞轻量 UI 和可执行闭环 |
| 完整隐私保留/脱敏策略 | P2/P3 | 竞赛模拟数据阶段可使用导出清洗；真实校园试验前必须补齐 |

这意味着不能取消可信输出建设，但应把工程量集中在“最终输出不会错、评委能看到证据、失败仍可演示”，而不是先追求所有内部文件的对抗篡改能力。

## 4. 竞赛导向阶段计划

### Phase Demo-0：两天内关闭现场阻断项

1. 将 IERS/leap-second 策略移入正常计算入口。
2. 修复 BLOCKED 公共返回；Review 暂时禁用 Qwen 自由补充。
3. 修复“今晚”、M42 高度表述、案例三 16/30 分钟冲突和复盘表格。
4. 区分科学可见窗口与建议活动时段。
5. 统一 `skills.yaml` / package / README 版本和能力声明。

**验收**：README 三案例连续运行；M31/M42 无互相矛盾文案；模型失败时核心结果仍交付；结构化案例无事实泄漏。

### Phase Demo-1：完成一页轻量演示

1. 预载 M31、M42、复盘三个案例。
2. 显示实时阶段进度和确定性回退状态。
3. 同屏显示高度曲线、活动包、关键 Claim 来源和验证状态。
4. 导入日志后显示 before/after，并生成可执行下一轮输入。
5. 提供已验证运行复现按钮，应对现场网络不稳定。

**验收**：不打开终端完成完整主线；模型超时不会中断；一名不熟悉代码的队员可在 8 分钟内独立演示。

### Phase Demo-2：补核心技术答辩证据

1. 完成 Claim + variant 语义重放，加入联动篡改测试。
2. 修复 Chat 统一 finalize、Manifest/Report 和模型调用聚合。
3. 完成 Review ID-only 或继续明确保持确定性 review。
4. 生成裸 Qwen / 旧过滤 / Claim 模式对照表。

**验收**：能够现场回答“如果模型完全错误，用户看到什么”“Qwen 到底做了什么”“下一轮为什么发生变化”。

### Phase Demo-3：真实用户和材料打磨

1. 组织一次小规模校园观测或完整模拟演练。
2. 记录准备用时、找到目标成功率、新手理解度和问题反馈。
3. 用真实数据替换当前案例三中的模拟矛盾备注。
4. 完成 10 分钟视频、20 页内材料和第二台电脑复现。

**验收**：技术深度、科学准确性、应用价值和可复现性各至少有一组可展示证据。

## 5. 推荐的 10 分钟演示主线

1. **0:00-1:00**：说明传统校园观测流程分散、难查、失败后不复盘。
2. **1:00-2:30**：加载 M31，展示本地天文计算和高度曲线；Qwen 只选择批准 Claim/表达顺序。
3. **2:30-4:00**：展示科学可见窗口、建议活动时段、活动包和 Claim 来源。
4. **4:00-5:00**：加载 M42，3-5 秒展示不可观测原因、替代目标和确定性回退。
5. **5:00-7:30**：导入一次效果不佳的日志，展示证据强弱、三类偏差和 before/after 下一轮计划。
6. **7:30-8:30**：点击重新生成下一轮活动包，证明闭环真的改变输出。
7. **8:30-9:30**：展示 Manifest、模型采用/拒绝记录和裸 Qwen 对照。
8. **9:30-10:00**：总结校园实训价值和真实试验结果。

现场不要同时跑多个真实模型调用。一个实时 Qwen 调用足以证明集成，其余步骤优先使用本地确定性计算或明确标注的已验证运行复现。
